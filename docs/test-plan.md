## 1. Мета

Підтвердити, що застосунок поводиться так, як описано в `docs/spec.md`, і
забезпечити регресійний набір автотестів на п'яти рівнях: юніт, API,
компонентні, end-to-end і UI. Будь-яка поведінка, що суперечить пункту
специфікації, вважається дефектом.

## 3. Підхід

- **Тестування на основі вимог.** Кожен пункт spec у скоупі має щонайменше
  один тест-кейс; трасування наведене в розділі 9.
- **Найнижчий рівень, на якому видно поведінку.** Логіка тестується на рівні
  юніт-тестів, контракт API і доступ до даних на рівні API, рендер і взаємодія
  на рівні компонентів. Сценарії через кілька сторінок і поведінка браузера
  перевіряються на рівнях E2E й UI.
- **Техніки:** граничні значення (довжина пароля, межі цін, кількість,
  пагінація), класи еквівалентності (валідні й невалідні вхідні дані),
  таблиці рішень (злиття кошиків, default-адреса), переходи станів (сесія:
  гість → вхід → refresh → вихід), негативне тестування й тестування доступу
  (чужі дані).
- **Тест має падати на зламаному коді.** Очікувані значення рахуються вручну,
  а не тим самим хелпером, що й код. Перевіряється результат, а не сам факт
  виклику мока (`testing-guide.md`).

## 5. Рівні тестування та інструменти

| Рівень | Префікс | Що перевіряє | Інструмент | Розташування | Команда |
|---|---|---|---|---|---|
| Юніт | `U-` | Чиста логіка без I/O | Jest | `apps/api/src/**/*.spec.ts`, `packages/shared/src/*.spec.ts` | `pnpm --filter @school/api test`, `pnpm --filter @school/shared test` |
| API | `A-` | HTTP-контракт, статуси, cookie, БД, доступ | Jest + supertest + Postgres | `apps/api/test/*.e2e-spec.ts` | `pnpm --filter @school/api test:e2e` |
| Компонентні | `C-` | Один React-компонент: рендер, взаємодія, помилки | Vitest + Testing Library | `apps/web/tests/*.test.tsx` | `pnpm --filter @school/web test` |
| End-to-end | `E-` | Користувацькі сценарії через кілька сторінок | Playwright | `e2e/*.spec.ts` | `pnpm --filter @school/e2e test` |
| UI | `UI-` | Теми, адаптивність, клавіатура, доступність | Playwright (+ `@axe-core/playwright`) і ручні перевірки | `e2e/ui/*.spec.ts`, розділ 7.7 | `pnpm --filter @school/e2e test ui/` |

Пріоритети: **P1** — безпека, гроші, втрата або витік даних; **P2** — основна
функціональність; **P3** — UX, косметика, рідкісні граничні випадки.

#### Ручний чек-лист (exploratory, один прохід на реліз)

- [ ] Стани завантаження, порожні стани й помилки мережі (зупинити API) на кожній сторінці
- [ ] Подвійний клік по «Add to cart», «Save», «Sign in», «Register» не дублює запити

- [ ] Лист скидання пароля в Maildev: тема, текст, посилання веде на `/reset-password` з токеном
- [ ] Перемикання теми не скидає стан форм і кошика
- [ ] Тексти помилок зрозумілі й не розкривають внутрішніх деталей (стектрейси, SQL)
- [ ] Заголовки сторінок (`<title>`) осмислені й різні
- [ ] Масштаб браузера 200 %: контент читабельний, нічого не обрізано

## 8. Критерії

**Вхід:** середовище піднято за розділом 4; база в seed-стані; збірка
API й web без помилок.

**Вихід:**
- Усі P1-кейси виконані й пройдені або мають заведений дефект із погодженим рішенням.
- ≥ 95 % P2-кейсів виконано; відкритих дефектів P1 немає.
- Кожен пункт spec у скоупі пов'язаний щонайменше з одним пройденим тестом.
- `pnpm test` зелений локально й у CI.

**Призупинення:** стенд недоступний; зіпсовані seed-дані; блокер у
вході або кошику, що унеможливлює подальші сценарії.

**Відновлення:** після усунення причини й повторного `pnpm db:reset`.

## 10. Дефекти

Процес за `docs/workflow.md`: дефект — це розбіжність із конкретним пунктом
spec, підтверджена кроками відтворення. Виправлення: гілка `fix/<опис>` →
коміт із тестом, що падає → коміт із фіксом → PR з SHA обох комітів.

| Серйозність | Опис | Приклад |
|---|---|---|
| Critical | Безпека, витік чужих даних, неправильні гроші | Доступ до чужого кошика; знижка порахована неправильно |
| Major | Основна функція не працює або порушує spec | Злиття кошиків губить товари; немає повернення на сторінку після входу |
| Minor | Функція працює з відхиленням | Порядок при однаковій ціні нестабільний |
| Trivial | Косметика | Відступи в темній темі |

Шаблон звіту: ID spec · середовище · передумови · кроки · очікуване (цитата
пункту) · фактичне · серйозність · рівень тесту, що ловить дефект.

## 11. Ризики

| Ризик | Вплив | Захід |
|---|---|---|
| E2E змінюють dev-базу | Нестабільні повторні прогони | `pnpm db:reset` перед прогоном; унікальні користувачі в тестах |
| API-тести ділять одну `school_test` | Взаємний вплив | `--runInBand`; кожен тест створює власні дані |
| Перевірка строків дії (15 хв / 30 днів) | Повільні або нестабільні тести | Фейковий час у юніт-тестах; на рівні API — записи з минулою датою |
| Playwright не підтримує Ubuntu 26.04 | Розбіжності з CI | Override платформи локально; еталон — CI |
| Тільки Chromium | Пропуск дефектів у Firefox / Safari | Поза скоупом; за потреби — додати projects у `playwright.config.ts` |
| Тести, що проходять без перевірки поведінки | Хибне відчуття покриття | Очікування рахуються вручну; кожен новий тест спершу перевіряється на зламаному коді |

## 12. Порядок виконання

1. **P1 юніт і API:** сесії й токени, ізоляція даних, гроші, кошик.
2. **P1 E2E:** вхід / вихід / повернення на сторінку, reset пароля, збереження й злиття кошика.
3. **P2 юніт, API, компонентні:** каталог, профіль, адреси, головна.
4. **P2 E2E та UI:** теми, доступність, клавіатура.
5. **P3 і ручний exploratory-прохід.**
6. Регресія: повний `pnpm test` на кожен PR (CI).
